# installer/

Build script for the installer (ARCH-2). Standard library only.

- `build.py`: `check`, `fetch`, `build`, `verify` (see its docstring). Expected refusals are typed errors (`HashMismatch`, `MissingTool`, `PinsError`, `ElevationRefused`, `CompileError`, `PublishedMismatch`), printed as one line, exit 2.
- `pins.json`: the only source of hashes: NSIS 3.10 portable zip (url, sha256) and the fixed compile inputs (defines, script commands, flags). The zip hash was recorded on first download (trust on first use); confirm it against the publisher before relying on it.
- Git and the container engine are only checked, never installed. The zip is downloaded into `$XDG_CACHE_HOME/ecosystem-installer` (default `~/.cache/ecosystem-installer`), per user; the script refuses to run as root.
- Fixed inputs (INST-REQ-013): `SetDateSave off`, `Unicode true`, `SetCompressor /SOLID lzma`, dictionary size, sorted file list, no date or time macros. Passing the script commands with `-X` and the resulting equal hashes are INFERRED, not yet proven (INST-REQ-014); SL-4's guest run compiles for real.
- The repository holds no installer binary and no signature (INST-REQ-005); a release publishes only the expected sha256.
- A hand-test kit for the interactive installer in a Windows VM (#137): [VM-TEST.md](VM-TEST.md) is the checklist and `guest/vm-state.ps1` the read-only report of the footprint; the kit's `installer.exe` is built outside Git.
- Build and hand-test on your own Windows PC (#235): [BUILD-WINDOWS.md](BUILD-WINDOWS.md) builds the same kit on the real Windows PC with one VS Code task, `Installer: build test kit` ([tools/build-windows.ps1](../tools/build-windows.ps1), #243). It can then run the kit in Windows Sandbox, and it reports UI bugs with the `installer-ui` issue form.

### VM kit build inputs and cache (#209)

From a clean checkout, with a stand-in payload outside Git:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m installer.guest.vmkit build --out ~/work/vm-kit/$(git rev-parse HEAD | cut -c1-12) --payload ~/work/vm-kit/stand-in-payload.txt
```

The kit uses the selected checkout, payload and pinned NSIS ZIP. The ordinary
builder keeps `nsis-3.10.zip`, the extracted `nsis-3.10/` tree and
`work/filelist.txt` in its per-user cache. Every fetch/build downloads the ZIP
again, checks its SHA-256 against `pins.json`, deletes the old extracted tree,
and extracts the verified ZIP; the work file list is overwritten.

The kit generator instead gives its builder subprocess a fresh temporary
`XDG_CACHE_HOME`. The entire temporary directory (ZIP, extracted tree and work
files) is removed on success or failure; an existing user cache is neither read
nor changed. Python bytecode writes are disabled for the builder, and the command
above disables them for the generator too. No build cache remains outside
`--out`. Ordinary `installer.build` callers retain their existing cache behavior.
On non-Windows hosts, the builder still uses the host's `makensis` when the
verified ZIP has no native compiler; cache isolation does not change or pin that
existing compiler selection.

## NSIS reference

Before changing an NSIS item, read its [reference row](nsis/REFERENCE.md) for the pinned
doc page, v3.10 behavior and current use sites. Add new items to `installer/reference.py`,
then run `python3 -m installer.reference build` from the repository root. `python3 -m installer.reference check`
is the same offline drift check run by the unit tests.
Regenerate its [pinned path manifest](nsis/reference-pins.txt) from local upstream clones with `python3 -m installer.reference pin --docs <docs-clone> --source <source-clone>`.
Any edit under `installer/nsis/` that moves a referenced line makes the unit gate fail with
`REFERENCE.md is stale` until you rerun `python3 -m installer.reference build` and commit the result.

## Trust chain (`trust.py`, `nsis/trust.nsh`, `nsis/main.nsi`)

- Fingerprint file format (published and stored): exactly one sha256 fingerprint; none, or two different ones, is refused. `build.py` reads the published file with the same parser. The stored file is 64 lowercase hex digits and a newline.
- First run: the user must confirm the fingerprint against the two published places, then it is stored. Same signer: no pause. Other signer: stop, show both, ask again (silent runs stop, exit code 3).
- Key replacement (inferred, design choice): a four-line statement signed by the old key; accepted only when the stored key signed it. The signature check is injected (fake on the host).
- `main.nsi` holds one include line per `.nsh`.
- Trust boundary: the NSIS code gets the signer fingerprint as `/SIGNER=<64 hex>` from the launcher, which has done the signature check before it starts. `trust.nsh` refuses a value that is not 64 hex but cannot verify who signed.
- Signer page (INST-REQ-103, #331 item 10): a run with a window started without `/SIGNER=` or with an empty one (a double click) is not refused: `TrustCheck` leaves the fingerprint to the first page, `Page_signer` in `trust.nsh`. Its help text: "Type the signer fingerprint: the 64 hex digits published in the two independent places. Then select Next."; its one box is labelled "Signer fingerprint (64 hex digits)" and takes upper or lower case (stored in lower case). Next with a value that is not 64 hex digits shows a box naming the problem (`/SD IDOK`) and keeps the page. A valid value gets the same checks as a given one (`TrustVerify`: same stored signer, no box; first run or changed signer, the Yes/No box, default No; Yes stores it); a No or a refusal from the page ends the run with exit code 3 (`SetErrorLevel 3`, `Quit`: `Abort` in a Leave function only keeps the page) and stores nothing. `Elevate_Raise` hands the checked fingerprint to the elevated copy as `/SIGNER=`, so that copy checks the same signer and asks nothing. A given malformed `/SIGNER=`, a silent run and the elevated copy without a signer are refused in `.onInit` as before (exit code 3); a given valid `/SIGNER=` skips the page. The page runs after `Update_Detect`, which switches an administrator window to the all-users folders: the page checks the signer in the user's folder (`SetShellVarContext current`) and runs `Update_Detect` again after it. `Elevate_SilentGate`, `Update_Detect` and `Runner_GitlabInstallGate` do not read the signer.
- NSIS stored-file reading is stricter than `trust.py`: the file must be 64 hex digits and at most a line end; an existing damaged file stops the installer (exit code 3), it is never a first run. Both confirmation boxes default to No.
- Experimental warning (#329): a run with a window shows one box first, before any trust box: "This is an EXPERIMENTAL installer (test build). It is not for production use: run it only where you can undo the changes." (OK only, `/SD IDOK`). It sits in `.onInit` after the command-line refusals (exits 50, 32, 33) and right before `TrustCheck`, so a malformed signer shows it and then the refusal (exit 3), and a missing one shows it and then the signer page; OK only closes it and no exit code changes. A silent run and the elevated copy (`$carried` 1, its first window already showed it) never show it. The window caption is "Ecosystem Runner Setup (EXPERIMENTAL)" (the uninstaller: "Ecosystem Runner Uninstall (EXPERIMENTAL)") and the branding line at the bottom of every page, between Cancel and < Back, reads "EXPERIMENTAL (test build)" (that line holds one short line only: a longer text is cut off). The `DisplayName` of the uninstall entry stays `Ecosystem Runner`.

## Input schema, host check and licences (SL-3)

- `schema.json`: the only description of the inputs (INST-REQ-020). `schema.py` validates it and generates `nsis/screens.nsh` (interactive pages, silent keys, secret refusal); `python -m installer.schema generate` writes it and `check` fails on drift. Secrets have a screen on the interactive "add secrets" page only and no silent key (D-R6-2); a secret on the command line, in a file or on standard input gives a typed exit code. Exit codes (one per failure class, distinct) are in `schema.json`; messages carry option names, never values.
- `hostcheck.ps1`: the read-only "will it work?" check; its accepted editions must equal `schema.json` (a test compares them).
- `licences.py`: the two licence boxes (unticked, only when an image is chosen, both needed) and the local 0600 licence record with a UTC date; it opens no network.
- The pinned image list lives in `schema.json` (`images.list`: container type, version, label, tag, repository and digest, with where and when the digests were read); a null digest is a typed refusal (`image-not-pinned`).
- Elevation and footprint (SL-4): `footprint.json` names the one folder, one service, one uninstall entry (and the documented per-user exceptions), the elevated markers and the exit code 38 for silent-not-elevated; `allowlist-read.txt` lists what may be read. `footprint.py` scans the NSIS and PowerShell source against both (`python -m installer.footprint check`, exit 2 on a violation; a test runs it). `nsis/elevate.nsh` holds the list screen, the silent gate, the no-administrator screen and `Elevate_Raise`, the ONE place that raises rights; the elevation approach is UNVERIFIED until the guest run, and only that function should need to change.

## Logs, time zone and data boundary (SL-7)

- Write limit: `FileWrite` calls in `nsis/log.nsh` are not checked (best-effort step log).
- `log.py` / `nsis/log.nsh`: step log, one line per step with command, exit code, output and a UTC ISO 8601 time; secrets are redacted. Only `display_hhmm()` converts, to plain HH:MM (no "Z", no "UTC"). The zone is stored by name only; daylight saving comes from the OS.
- `zones.json`: Windows-to-IANA table with country (445 rows, 142 Windows zones), generated by `zones_gen.py` from the Unicode CLDR `windowsZones.xml` of release-49 (file sha256 `5f902f94106a396cb7774f0b0e1ca4dfecb686494045350c0b4935d378e3913b`, published at raw.githubusercontent.com/unicode-org/cldr/release-49/common/supplemental/windowsZones.xml) and pinned by sha256 (in the file, in `log.py` and in `tests/test_installer_zone.py`). The first row of a zone is the CLDR default, the country is the territory the name is listed under, and the 18 names CLDR still spells the old way (tz data without backward links lacks them) carry the current tz name (`RENAMED`); the selection rule is in the generator's docstring and in the file's `how_obtained`. Regenerate: fetch the file by hand (the generator, the installer and the tests never touch the network; the XML is never committed), run `python3 -m installer.zones_gen --source windowsZones.xml --expect-sha256 <sha256> --tag <release> --out installer/zones.json`, and copy the printed `sha256_of_zones` into `ZONES_SHA256` in `log.py` and `PINNED` in `tests/test_installer_zone.py`. `tests/test_installer_zones_gen.py` compares the generator output with the committed file byte for byte when `ZONES_SOURCE_XML` names a copy of the recorded XML, and skips with that reason otherwise. Attribution: Copyright © 1991-2013 Unicode, Inc.; terms of use at www.unicode.org/copyright.html.
- `diagnostics.py` + `diag-allowlist.txt`: the diagnostics zip is written locally from the allow-list only (the file is the single source; the operator reviews every change). Text values that are not plain (paths, URLs, variables) become `[redacted]`; names passed as `deny` (user, host) are removed. The path is shown to the user, who sends it himself; there is no upload code.
- `netpolicy.json`: the three allowed destinations (NSIS source, the user's own forge, the vendor registry holding the pinned digest) and the forge names that must never appear; a test scans every installer source against it.
- `steps.jsonl` (the step log) is NOT part of the diagnostics zip and must not be sent: it holds commands and output. Redaction in `log.py` is best-effort (keyword values, Bearer/Basic, quoted values, percent-encoded keywords, URL user info, licence-key shapes); never put a secret on a command line.
- A process exit is a JSON integer. If the process could not start or timed out, the record has `"exit_code": null` and `"exec_error": "error"` or `"timeout"`. Diagnostics preserve the null rather than inventing a process exit.
- The installer resolves its machine log path in the all-users shell context before validating options. Refusals 30/31/35/36 append only to an existing, writable machine log: if the folder or log is missing, they create nothing and write no line. Their exit code is unchanged.
- The zone pin detects edits only; it does not prove the table is right. The table follows the CLDR file by construction; whether it fits the zone names real Windows PCs report (risk U-4 in the spec) has not been compared yet on L1 or L2.
- `log.nsh` writes step names and commands without escaping: callers pass installer constants only. The log file is `$APPDATA\EcosystemRunner\steps.jsonl` (inside the footprint). UTC time = local time + `ActiveTimeBias` (includes daylight saving), integer-only, no plugin; one read line for that registry value was added to `allowlist-read.txt` with commander approval. `log.utc_from_local()` is its twin and a test runs the real NSIS body in a small interpreter against it. Not yet run on a real Windows guest.
## Runner modes (SL-5)

- `runners.py`: one mode switch (`github`, `local`, `gitlab`; delivery order in that sequence). A PC serves one forge: the other is refused (`second-forge-refused`). Registration only at a typed `https://` address, no default. GitLab: install only when elevated, service under the footprint's virtual account, a missing log-on right is `logon-failure`, the token exists only in `config.toml` (0600) under the install folder. Local only runs check, build, SBOM (stdlib CycloneDX, in process) and unittest by command, no service. Pinned minimal tooling choice (open decision O-4) is the `LOCAL_COMMANDS` table. These error kinds have no exit code yet in `schema.json` (outside this slice).
- `image.py`: pulls by pinned sha256 digest only after both licence boxes; no push, save or export.
- `nsis/runner-*.nsh`: the mode switch and the elevation gate; no command is executed from them.
- SL-5 hardening: the forge is recorded in a permanent marker (state folder and install folder; a `config.toml` or the mode file also counts) before any registration and is never cleared; damaged state is `state-corrupt`. Addresses are parsed (https, host, no user name or password, no space, control or quote character; optional pinned host); tokens with such characters are refused (`bad-secret`). `config.toml` is created fresh (`O_EXCL`, no link followed, 0600 at creation) and `system.restrict_acl` (SYSTEM, Administrators and the service account only) runs before the token is written; it is removed on any failure. The injected `forge.register` and the system adapter must never put the token on a command line or in a log; anything they log goes through `installer/log.py` `redact`. The SBOM skips `config.toml` and symlinks. The Windows `restrict_acl` adapter is not built yet (guest proof).

## Update, rollback, repair, uninstall, extension contract (SL-6)

- `update.py`: `update` (backup, stop, swap, start, health check, restore; only `program/` is replaced and the screen text is only "previous program files restored"), `repair` (idempotent, never creates keys or registers), `uninstall` (offline; lists forge leftovers with the exact place and says a registration is gone only if the forge confirmed it), `check_major` (pure major-version check, also used for the extension). The health check is the service staying running for `HEALTH_SECONDS` and, in forge modes, the runner online. `state.schema.json` fixes the `installer-state.json` shape. `extension-contract.md` states what the extension may do. `nsis/update.nsh` and `nsis/uninstall.nsh` mirror the refusal text and the removals; the Windows system adapter is proven in the guest.
- `winsys.py` (SL-10): the real Windows `system` for `runners.py` and `update.py`: thin wrappers over `sc.exe`, `icacls.exe`, `reg.exe` (64-bit view) and `powershell.exe` with fixed argument lists, no shell, injected process runner and clock, typed errors (`LogonFailure` for service code 1069). `nsis/winsys.nsh` runs the same commands, elevated phase only (exit 38 otherwise). Proven on the host with fakes; the guest run proves the real commands.
- Uninstall hardening (UNINST): `update.OWNED` now includes `uninstall.exe` (the NSIS install writes it into the folder; before, it stayed, the folder could not be removed and the report said "folder contents (other files kept)"), and a read-only file no longer stops the Python removal: the read-only bit is cleared and the delete retried once, else the error is raised as before (a link is never followed). `nsis/uninstall.nsh` mirrors `winsys.py`: after `sc stop` it polls `sc query` until STOPPED or error 1060 (30 polls, one second apart), retries a stop refused with 1061 (1, 2, 4, 8, 8, 8 s), reads the `sc delete` result (0, 1060 and 1072 are fine) and removes the folder in this order: first everything except `uninstall.exe` (every entry through `un.Tree_Remove`, which never follows a link: see SL-23 below; five retries one second apart, because `runner.exe` may still be mapped), and only when nothing else is left `uninstall.exe`, then the folder, and the uninstall entry last. A single `RMDir /r` on the whole folder deletes everything it can reach, `uninstall.exe` included, even when a held-open file keeps the folder (measured on the guest: the entry then pointed at nothing), so that order is not used. Anything else, or a leftover, is a stopped uninstall: a message, exit code 40 (`uninstall-stopped` in `footprint.json`, the kind of `update.UninstallStopped`; no numeric code existed for it before), and neither the uninstall entry nor `uninstall.exe` is deleted, so the uninstall can be run again. One edge, decided: if `uninstall.exe` is already deleted and only the empty folder cannot be removed, nothing can be run again, so the uninstall entry is removed anyway, the message names the folder to delete by hand, and the exit code is still 40. `un.onInit` is an administrator gate, the same `UserInfo` test as the install under an `un.` name: not an administrator gives exit code 38 (`not-elevated`) before anything is touched, with one message first when interactive. It is defence in depth only: a standard user cannot start the installed `uninstall.exe` at all (the folder is locked; measured on the guest: access denied), so there is no relaunch with `runas`. NSIS has no report file: the message and the exit code are its report, the state tells the rest. The Python reference model (`update.uninstall`) follows the same order: service, folder (`uninstall.exe` is the last file of `update.OWNED`, so while anything else cannot be removed it stays), and the uninstall entry last, so a failed step leaves the entry; `UninstallStopped` and its `report` name what remains (the service, the paths still in the folder, the entry), and a folder that is already gone is accepted so that a stop at the entry step can be run again.
- What a caller can see of an uninstall (measured on the guest). The registered `UninstallString` and `QuietUninstallString` have no `_?=` and are unchanged. In that default start the first stage copies itself to `%TEMP%`, returns 0 after about a second and the copy works on asynchronously, so no exit code (38 or 40) reaches the caller: the visible signal is the state, and on a leftover the folder and the uninstall entry remain. With `uninstall.exe /S _?=<folder>` the exit code is visible (0, 38 or 40) and the service is removed, but the running uninstaller cannot delete itself, so `uninstall.exe` stays in the folder. It alone is not counted as a leftover (the entry is removed, exit code 0); any other file is (exit code 40, the entry kept). The caller of the `_?=` form removes that one file afterwards.

## Update and repair (SL-19, #100)

- `Update_Detect` (called from `.onInit` after the silent gate) reads `installer-state.json` (admin only; a non-admin run stays a first install). No file means a first install (`Install_Footprint` unchanged). `schema_version` 1 and `installer_version` as three plain numbers are required, else exit 45 and nothing is changed. The same version is a repair; an older installed version is an update; a newer installed version or another major version is refused (exit 41).
- Update order (INST-REQ-040): folder check and lock, one confirmation (interactive only; silent answers yes), backup of `program\` and `service.json` to `backup\`, `sc stop` confirmed STOPPED (1061 retried with backoff; not confirmed means exit 43, nothing written), program files swapped (`SetOverwrite try` always: with `on` or `ifdiff` a failed write in a silent installer aborts with exit 2 before the restore can run), start, 30 one-second health polls, the state file written last (mode and forge address kept), and then `backup\` is removed. A failed swap, start or health check restores the backup and exits 42 with the one text "previous program files restored"; a restore that fails exits 44 and keeps `backup\`. A failed backup exits 43. Configuration, logs, keys, registration and the state file are never touched by the swap (INST-REQ-038).
- What is left after an update: no `backup\` folder (INST-REQ-040 and 041 do not promise retention). What is left after a failed restore: `backup\` with the previous program files, untouched. The backup is a restore point only when the marker `backup\complete` is there: it is written last, after the copy and `service.json`, and removed first on success. The next update, if the marker exists, restores the backup first and never deletes it; if that restore fails it exits 44 and keeps the backup; if it works a new backup is made. A backup without the marker (half-made, or left behind because its removal failed after a good update) is stale: it is removed and never restored over a good program. Backup removals use `Tree_Remove`: an old backup that cannot be cleared stops the update before anything is copied (exit 43); the other removals are best effort and leave one `update-backup-cleanup` line in the log. Stale-backup behaviour is MEASURED on Windows (`guest/update-smoke.ps1`, cases U-B3 to U-B5 under "Guest harnesses"): a locked file in a stale `backup\` stops the first update with exit 43, and a second update after the release finishes it. `update.py` follows the same marker rule, but clears an old backup with `rmtree` inside its `try`: a failure there is `BackupFailed` (exit 43), the same end result by a different route. A crash between `Update_WriteState` and the marker `Delete` leaves a stale marker beside a good program; the next update restores the old program first and then swaps (harmless unless that swap fails); the same holds for a marker that cannot be deleted (a failed `Delete` is ignored, and in `update.py` a failed `unlink` of the marker is ignored too). A backup made by the code before this PR has `program\runner.exe` and no marker: the new code does not trust it, it removes it and never restores it. A path that is not there is gone for `Tree_Remove` (`$2` = 0, nothing deleted; READ in FileFunc.nsh, not measured on Windows): without that rule the first update, with no `backup\` folder, would fail closed with exit 43. The update tests run a MODEL of `Tree_Remove` (`UpdateWorld.native_Tree_Remove`); `tests/test_installer_sl23b.py` `Parity` runs the model and the real text of `tree.nsh` on the same shapes, and that test is what keeps the model in step with the text.
- Guest cases for the Windows run of PR 101: MEASURED, every one as READ (`guest/update-smoke.ps1`, "Guest harnesses" above): a junction at `backup` and a junction at `program` (exit 39, nothing changed and no link followed), a locked file in a stale `backup` (exit 43, then 0 after the release; share modes None and ReadWrite), a stale backup seeded before an update (0), and the FIRST update with no `backup\` folder (0, update applied).
- State file (INST-REQ-039): read as one line; a first line of 1023 characters or more (the `FileRead` limit) is refused with exit 45 and the file is left unchanged, and `"schema_version": 1` must be followed by a comma or a closing brace (so 12 is refused). `Update_WriteState` writes the whole new line from the known fields (forge address, new version, mode, schema version, sorted keys, a line feed), byte for byte what `update.py` `write_state` writes, and never writes back a truncated read.
- State values copied back (#228): `Update_WriteState` copies the old `forge_address` and `mode` text verbatim, so detection (`Update_Field` in `Update_ReadState`) refuses, with exit 45 and nothing changed, a value that is not a valid JSON string body: an escaped closing quote (an odd number of backslashes before it, so the value really goes on), a backslash that does not start `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, `\t` or `\u` with four hex digits, or a raw control character. Valid escapes are copied back byte for byte, so the rewritten line is what `update.py` `write_state` writes. The Python writer and `state.schema.json` stay unchanged: `json.dumps` always writes a valid value, and a schema `pattern` would refuse addresses that are valid today.
- Repair (INST-REQ-042) stops the service, rewrites the program files (`SetOverwrite try`, so an identical file is written again; the end state is the same on every run), recreates a missing service and uninstall entry, starts and checks the service. It never creates a key and never registers. The state file is rewritten with the same version.
- Exit codes: 41 major version mismatch or a newer installed version, 42 update restored, 43 update or repair not applied (confirmation declined, stop not confirmed, backup copy failed, repair program write failed, repair health check failed), 44 restore failed (backup kept), 45 state file damaged. The update and repair stops are a logged step, `SetErrorLevel` and `Quit`, with a message box first in interactive runs (`/SD IDOK`); the exceptions are `Licence_WriteRecord` (exit 37: `SetErrorLevel 37` then `Abort`), `Winsys_FolderCheck` (`Abort` with 39), `Winsys_FolderLock` (`Abort` with 2) and `Page_mode_Pre`, which aborts to skip the mode page. Registered in `footprint.json` like 40 of the uninstall slice. Not used here: 46 is SL-16b (`image-pull-failed`) and 47 is SL-17a (the first registration failure).

  A failed uninstaller or state write is logged before the run exits. No uninstall registry values are published by the failed step; an existing entry is not removed. A state file may be empty or incomplete. NSIS 3.10's `FileClose` discards the `CloseHandle` result (`Source/exehead/exec.c:1378-1383`): the check after close detects a preceding `FileWrite` error, not a close-only failure.

  If `nsDialogs::Create` returns `error`, the installer aborts that custom page before it creates controls or tries to show the dialog. This is a page abort, not a new process exit code.

- Licence record and image pull (decision, REV107 A4): an update and a repair end like a first install: `Licence_WriteRecord` (a failed write exits 37), then `Image_Pull` (a failed pull exits 46) as the very last step, after the program is in place and the state file is rewritten. A failed pull does NOT roll the swap back: program and service are consistent, and a repair retries the pull. A failed update (the restore path, exit 42) and a stopped run (exit 43) call neither.

- The mode page is shown only on a fresh install: `Page_mode_Pre` skips it (`Abort`) for an update or repair.

## Typed values (SL-16a, #102)

Every value the user types is checked, on the screens and in a silent run, by one rule set written once in `installer/schema.json` (the kind plus the attributes `https_only` and `no_blank`) and generated into `installer/nsis/screens.nsh` (`Check_<id>`, `Val_*`). `validate_values` in `installer/schema.py` applies the same rules; `tests/test_installer_sl16a.py` runs one table of values through both.

- **Rules.** text and path: one line, no double quote. url: `http_proxy` is `http://` or `https://` with a host; `github_url` and `gitlab_url` (`https_only`) are `https://` with a plain host (no user name, password or brackets, optional port of one to five digits) and none of space, quote, backslash or control character. list: no empty item (so no leading or trailing comma). choice: compared without case and stored in lower case. licence: yes or no. `image_variant` and `image_year` come together; `image_year` holds the version of the pinned list (the tag without its container type, for example `2026q1patch2`). Secrets (`no_blank`): none of space, quote, backslash or control character. Only tab, CR and LF are looked for among the control characters.
- **Screens.** Each page keeps its control handles in `$ctl_<id>`; `Page_<page>_Leave` reads them into `$in_<id>` and checks every NON-EMPTY field. A bad value shows ONE message (`<field>: <what is wrong>.`, with `/SD IDOK`) and the page stays. An empty field means not given, and `required` is deliberately NOT enforced for `install_dir` (`validate_values` does). The secrets page reads the three masked fields the same way; the message names the field and never the value, and a secret is never shown, logged or written to disk by this slice.
- **Layout and help (#329).** A page with a `help` text in `schema.json` (every generated page except the NI docker image page, which is being replaced separately) starts with that text as a two-line label at the top; then each field is a label at y (8u) and its box at y+9 (12u), and the next field starts at y+24, so no box overlaps the next label. Radio buttons keep a 16u pitch and check boxes a 24u pitch below the help. A page without `help` keeps the old 18u pitch, where each box overlaps the next label by 2u. The help texts only say what the code does (empty box skipped, https:// only, both licence boxes). The no-administrator and elevation pages already start with their own explanation.
- **Silent run.** `ValidateSilentKeys` runs in `.onInit` after the mode and before `TrustCheck`, only when `/S` or when the elevated copy was handed the typed answers (SL-21b, below). The order of the exits is: 50 (a command line of 1023 characters or more, which NSIS cut: the log holds the step `cmdline-too-long` and the word `command-line`, and it runs before everything else), then 32 or 33 (the secret refusal, which runs before this), then 30 for a command line that ends inside a double quote (an unclosed quote would hide every later key; the log holds the fixed words `bad-value` and `command-line`, never the swallowed text), then the names: a word starting with `/` that is not a schema key and not `/S`, `/D`, `/NCRC`, `/ELEVATED` or `/SIGNER` exits 31; a schema key with no `=` or an empty value exits 30. Then every given value is checked and a bad one exits 30. The log carries the key NAME only: a typed exit writes exactly ONE log line (the step, with the key name and no value) and nothing else. No keys leaves the run as it was. Every read of the options goes through the one reader below, the elevated relaunch included (SL-21b, #117: `Elevate_Raise` builds what it hands over with `Cmdline_Has`, `Cmdline_Get` and `Cmdline_Quote`). The mode value is checked earlier by `Mode_FromSilent`, so a bad `/MODE` exits 30 even next to an unknown key.
- **One command-line reader (SL-16e).** `installer/nsis/cmdline.nsh` reads the command line for everything: the secret refusal, the check of the names, the 14 keys, every choice's silent selection and the trust signer (`/SIGNER=`); `${GetOptions}` and `${WordFind}` are not used. The elevated relaunch goes through it too (SL-21b, #117): `Elevate_Raise` builds the string it hands over with `Cmdline_Has`, `Cmdline_Get` and `Cmdline_Quote`. It skips the program name itself (a name that starts with a double quote ends at the next double quote, or at the end of the text when there is none; any other name ends at the first blank or tab; this replaced `${GetParameters}`, #136, REPORT L3), so a path such as `setup - Copy.exe` or `C:\Tools /v2\setup.exe` is never taken for an option, and scans the rest left to right. A token ends at a blank or a tab outside quotes. A double quote opens and closes a group (blanks and tabs inside stay in the value) and is dropped; there are no escapes: a backslash before a quote is an ordinary backslash, so `/INSTALL_DIR="C:\dir\"` ends its group at that quote. Apostrophe and backtick are ordinary characters (a lone one hides nothing). An unclosed quote runs to the end of the command line (the next bullet says what that means for the secret refusal and for the exit code). A key is the token text up to its first `=`, compared without case; its value is the rest (it may hold `/` and further `=`), so an unquoted `/GITHUB_URL=https://github.com/owner/repo` is read whole, exactly like the same value in double quotes, and a whole token may be quoted too (`"/INSTALL_DIR=C:\Program Files\x"`). The first token with a key wins, and a key never matches the start of a longer key. `Cmdline_Get` sets the error flag when the key is absent and clears it when found; it sets the flag again after its own `${If} ${Errors}` test, because `IfErrors` (so `${Errors}`) clears the flag it tests, and `Mode_FromSilent` relies on that. `Cmdline_Quote` wraps a value containing a blank or tab in double quotes. It cannot escape a literal double quote: the text and path screens reject one, the URL and list screens can accept one, and `Carry_One` refuses to carry such a value across elevation. `schema.parse_silent` (with `split_command_line`) gives the same answers; `tests/test_installer_sl16e.py` compares the two on a corpus. The two limits of `${GetParameters}` (a program of ONE letter and no extension, started as `s /FOO /S`, lost its first parameter, and a tab was not a separator) are gone with it. NSIS removes ` /D=...` and everything after it before the script runs, so the elevated relaunch loses it; this is kept as it is, and `schema.parse_silent` and the test model keep that text (probe row 9 differs from them on purpose). `$CMDLINE` is cut at 1023 characters, which would hide every key after the cut, so a command line of 1023 characters or more is refused with exit 50 (`cmdline-too-long`: one log step with the word `command-line`, nothing else written, interactive or silent), checked before every other command-line check; the longest line that is read is 1022 characters, program path and blank included. `schema.parse_silent` and `run_silent` take the length of the whole line as `command_line_length` and refuse it the same way; without a length they do not check.

The record `licence-record.json` is in the footprint folder (listed in `footprint.json` as `licence_record`), is written only with an image and both answers `yes`, equals `licences.write_record` byte for byte and never leaves the PC (INST-REQ-074).
- **Pull.** `nsis/image.nsh`: `nsExec::Exec '"$ImgEngine" pull $ImgRef'`, where `Image_Engine` looks only at `$PROGRAMFILES64\Docker\Docker\resources\bin\docker.exe` and then `$PROGRAMFILES64\Docker\docker.exe` (never a bare `docker`, never `$PATH` or `$EXEDIR`; neither found: exit 46 `image-engine-missing`, one box, install stays; `-DENGINE_EXE=<path>` overrides the search for tests only and needs `-DRUNNER_TEST_BUILD=1` too, else the compile fails with `!error`; the default is empty), output not kept (one constant `DetailPrint` says the pull can take a long time and that Cancel waits until it ends; there is deliberately NO timeout, an NI docker image pull can take hours), never `save`, `export`, `push` or `login`. Before pulling, it shows the constant line "Checking which container type Docker runs." and runs `"$ImgEngine" info --format {{.OSType}}` with `nsExec::ExecToStack`, using the same fixed engine path and with no timeout. If the probe succeeds, the answer is trimmed and compared with the chosen container type. A mismatch shows "Docker is running $R1 containers, but the NI docker image needs $in_image_variant containers. Switch Docker to $in_image_variant containers and run the installer again to repair.", then exits 46; a probe that fails is ignored and the pull is tried as before. `$ImgRef` is `repository@digest` from a table generated from `schema.json` (`Image_Ref`, like `image.reference`), never typed text. `Image_Pull` does nothing unless an image is chosen, the record exists and both answers are `yes`. A pair whose repository or digest is still null is not pulled: exit 36 (defence in depth: the gate and the page refuse it earlier). A failed pull exits 46 (`image-pull-failed`, step logged with no engine output) after one plain message; the install stays complete and removable: run the installer again to repair.
- **Schema.** Each `images.list` entry gets a `repository` (null until pinned, like `digest`); the schema check rejects a digest that is not `sha256:` plus 64 hex digits.
- **Repair.** Repair of an existing install does not pull or write the record until slice SL-19 is merged.
- **Registry password.** Not used. A pull that needs a login fails with 46; SL-17 designs how the password reaches the engine.
- **Exit codes.** On install-folder creation, 2 means descriptor setup failed (`folder-descriptor-failed`); 39 means the folder could not be safely created or claimed. 40 is uninstall, 41 to 45 are update and repair, 46 is the image pull, 47 is reserved for SL-17a.
- **Not verified on Windows (GUEST6, #94).** The licence and pull paths run only in the interpreter until a stub-engine guest run; all pinned digests and repositories are still null; the record is in `update.OWNED`, before `uninstall.exe`.

## Declining the administrator prompt (SL-21a, #111)

`Elevate_Raise` clears the error flag, raises the prompt once (`ExecShell "runas"`) and quits only when the hand-over worked. If the user declines, the flag is set: the installer shows one message (an exclamation box with OK and `/SD IDOK`: the installation needs administrator rights and has NOT started; Next shows the prompt again, Cancel leaves) and `Page_elevation_Leave` aborts, so the user stays on the page. Nothing is recorded about the decline: the variable the first version kept for it (`elev_declined`) was never read after the `Quit`, so it is gone. Cancel on that page ends the installer with NSIS's own exit code 1 (cancelled by the user), not 0 and not a code of ours. Unproven until a guest run: the real error flag after a decline, the page and that code 1; the probe is case (j) of `installer/guest/gate-probes.ps1` (`GATE-j-uac-a-stays-open`, `GATE-j-uac-b-box-exists` and `GATE-j-uac-c-exit-code-after-cancel`, which passes only for exit code 1).

## Handing the typed answers to the elevated copy (SL-21b, #117)

- **What crosses.** `Elevate_Raise` builds ONE parameter string for `ExecShell "runas" "$EXEPATH"`: `/NCRC` (only if the first window was started with it), `/SIGNER=<value>` (as given, or the fingerprint checked on the signer page when none was given), `/ELEVATED`, then every non-empty NON-SECRET answer as `/KEY=value` in schema order. `Carry_Answers` in `screens.nsh` is generated from the 14 public inputs of `schema.json`, so a secret is never in the string, a box, the log or a file; the secrets page of the elevated copy shows empty (delivering secrets is SL-17a, #105). A value with a blank or a tab is double-quoted by `Cmdline_Quote`. The fixed words come first and the answers after them (the first plan put them last): the fixed words claim their room first, and the NSIS stub reads `/NCRC` word by word, so nothing before it may confuse it. No answer key is passed through from the first window, so a first-wins collision cannot happen.
- **The first window's own words.** Only `/NCRC` and `/SIGNER=` pass through. `/D=` never reaches a script (the stub removes it), and any other word typed on the command line of an interactive run is dropped, so nothing typed before the prompt can exit 30 or 31 after it. `Cmdline_Has` compares without case, so a lower-case `/ncrc` is handed over as `/NCRC`, although the stub honours only capitals (accepted, not changed).
- **The elevated copy.** It is not silent, but it never shows the experimental box (#329): its first window did. `Carried_Detect` sets `$carried` when the run is not silent, has a bare `/ELEVATED` (no `=`) and has `/MODE=`; `/ELEVATED` alone, or without a mode, shows the wizard as before (else `install.nsh` would write `runner-mode.json` with an empty mode), and a silent `/S ... /ELEVATED` run is unchanged (exit 38 for a standard account, no box). With `$carried` set, `.onInit` runs the silent readers (`ParseSilentKeys`, `Mode_FromSilent`, `ValidateSilentKeys`, `Licence_SilentGate`) over the string, so the value rules, the exit codes (30, 31, 35, 36) and the logged steps are those of a silent run; every page except the secrets page aborts in its pre-function (`${If} $carried == 1`), and the secrets page is shown empty. A token it does not accept ends it as in the silent run, but, because a person waits, after ONE box that names the key (`Carried_Box`: `/WORK_DIR`, `licences`, `image`, never a value): "The administrator step did not accept the answer ... Nothing was started." Exits 32 and 33 (a secret on the command line) stay silent and unchanged: Rule R means the first window cannot hand over a word that gives them.
- **Rule R: what is NOT handed over.** A value is not carried when it holds a double quote (the reader has no escape; the text and path screens refuse a quote, the url and list screens do not, so such a value is refused here), when a blank is followed by `/` or `-` (the stub would read ` /S y` as the silent switch, ` /NCRC y` as no integrity check and ` /D=` as the end of the line; the secret refusal of the elevated copy would exit 32 on ` /GITHUB_TOKEN=` and 33 on a word `-`), or when it ends in a blank (the stub then reads the closing quote as the start of an argument and pairs every later quote the wrong way round, so the first word of a later quoted value, such as `/S x`, shows up as a switch). The first window then does NOT start the elevated copy: one box names the answers (labels only, never a value: "These answers cannot be handed to the administrator step, so it was NOT started: ...") and the user stays on the page to go Back and change them. A value that only starts with blanks, or holds a `-` or a `/` inside a word (`C:\Program Files\x/y`), crosses unchanged. A blank followed by `-` also refuses harmless values such as `Work -2024`: accepted.
- **Length.** The elevated copy's `$CMDLINE` keeps 1023 characters, program path and blank included, and cuts without a message (`NSIS_MAX_STRLEN` is 1024). `Carry_Begin` sets the room to 1022 minus the length of `$EXEPATH` minus 2 (the quotes round it); each token costs its length plus one blank (the first pays for the blank after the program path); a token that does not fit is refused, its label goes to the box and nothing is cut. The box names the first answer, in the order above, that no longer fits: with a very long work folder that is the LATER answer (for example "LabVIEW version"), not the long one. The elevated copy can read a whole line of 1022 characters; the first window refuses a line of 1023 or more before the administrator prompt, so a carried line never reaches exit 50 (#136, #186).
- **Updates and repairs.** The first window is not administrator, so its `Update_Detect` says "fresh" and every page shows; the elevated copy runs `Update_Detect` in `.onInit` (after the answers are read) and again in `Update_Route`: installed 0.1.0 gives update, the same version gives repair, a newer one exits 41, as before. The handed-over answers are ignored there except by the licence record and the image pull. `Page_mode_Pre` already skips the mode page for update and repair and is unchanged.
- **Back on the secrets page.** The secrets page is the first page the elevated copy shows. From the NSIS source (`Ui.c`, `ShowPage`): a page whose pre-function aborts is skipped, and Back through skipped pages reaches page minus one, which ends the dialog, so Back there would close the installer without a word. The page therefore disables the Back button (`GetDlgItem $0 $HWNDPARENT 3` and `EnableWindow $0 0`, only when `$carried == 1`); an ordinary run is untouched. Source-read, not measured on Windows.
- **Not verified on Windows (guest run, #121).** The UAC consent and the environment of the elevated copy; that `ExecShell "runas"` passes the string verbatim and whether it quotes the program path (if not, the room above is conservative by 2); the real cut at 1023; the Back button. The case to run: one real `ExecShell "runas"` from a probe installer started WITHOUT administrator rights, with a value holding blanks and a `/` not preceded by a blank (for example `C:\Program Files\x/y`), a refused value with a blank before `-`, a refused value ending in a blank, and a line over the limit.
